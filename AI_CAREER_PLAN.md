# RoleFoundry — Career Journey Playbook

This English playbook translates the original individual job-search process into product behavior. It complements the [integrated product plan](ai-career-platform-plan.md). It is not an actual job collection, assessment or application record.

## 1. Establish a direction

Collect a current resume, relevant experience, projects, region, workplace preference, salary expectations, language/work eligibility constraints, excluded industries, weekly available time and target timeline. Private contact details are not necessary for an initial capability review. Choose one or two primary role directions and a backup with an explicit reason.

## 2. Role pathways

| Direction | Typical learning sequence | Useful evidence |
| --- | --- | --- |
| AI/LLM application engineer | Python, Git/HTTP/SQL, APIs, LLMs, retrieval/tools, evaluation and deployment | Working service, tests, quality/latency/cost analysis |
| ML engineer | Python/SQL, statistics/linear algebra, baseline ML, validation, deep learning, serving | Correct splits, baselines and error analysis |
| Data analyst/scientist | SQL, statistics, Python/BI, business metrics, experiments, relevant ML | Reproducible analysis and justified recommendations |
| Data engineer | SQL/Python, modeling, ETL/ELT, scheduling, quality and cloud | Rerunnable pipelines and failure recovery |
| MLOps/platform engineer | Linux/Python, Docker/cloud/CI, serving, monitoring and versioning | Deployments, observability and rollback |
| Vision/edge engineer | Image processing, deep learning, detection/segmentation and inference | Real-scene errors and device performance |
| AI PM/consultant | Discovery, workflow mapping, AI constraints, prototype, evaluation and rollout | Interviews, requirements, alternatives and measured outcomes |
| Automation/operations | Process decomposition, data, automation tools, APIs/webhooks and exception handling | Time/error baseline, approval steps and recovery |
| Research/research engineering | Mathematics, optimization, deep learning, papers and experiments | Reproduction, rigorous experiments and research contribution |

These pathways are guidance, not blanket requirements. Actual education, seniority and domain expectations belong to individual job postings. Non-engineering creative and content roles use the same problem/evidence loop with role-appropriate artifacts.

## 3. Gather a bounded job set

Begin with 30–50 relevant, deduplicated openings within the user's chosen scope. Search company sites and supported job sources using role and skill terms, including classical ML, data, vision, product and automation. Record coverage limitations. Preserve company/title/source IDs, dates, conditions, required/preferred skills, uncertainty and the original application link.

Deduplicate by company/source identity and reviewed content. Keep multiple source links for a canonical opening. Recheck before applying and retain history when an opening closes. Do not interpret a broken fetch as confirmed closure.

## 4. Compare evidence to requirements

For each requirement keep the original wording, supporting personal evidence and judgment reason. Classify as supported, claimed but poorly evidenced, short-term learning opportunity, longer-term gap or unknown. Use the comparison to prioritize action; a percentage is not a hiring probability. Preferred conditions are not automatically mandatory.

## 5. Learn with an outcome

Start with recurring requirements across target jobs. Pick one main resource per stage, including a relevant DeepLearning.AI resource when available, then build a small outcome. A starting time allocation is 30% foundations/documents, 50% practice/debugging and 20% resume/interview work; adjust to the learner's situation.

Choose one main project and one focused exercise, rather than many unfinished courses. The learner should be able to modify, debug and explain the work. AI assistance is acceptable when verified and clearly described.

## 6. Project evidence

| Direction | Example artifact | What to evaluate |
| --- | --- | --- |
| LLM application | Domain document assistant | Held-out questions, citations, refusals, latency and cost |
| ML/data science | Churn/demand/anomaly model | Baseline, splits, leakage, error segments and business relevance |
| Analytics | Metric dashboard and experiment proposal | SQL definitions, inference limits and actionable decisions |
| Data engineering | Multi-source pipeline | Quality, reruns, scheduling and recovery |
| Automation | Extraction/classification/approval workflow | Baseline time, errors, escalation and human review |
| Product/consulting | Prototype and adoption proposal | Discovery, alternatives, evaluation, cost and rollout |
| MLOps | Deployed model service | Versions, CI/CD, monitoring and rollback |
| Vision/edge | Detection service | False positives/negatives, data shift and inference constraints |

Each artifact states the problem/audience, permitted data, baseline, method, fixed evaluation, actual results, failures and limitations. Include a reproducible guide or case study, a short demo, personal contribution and the scope of AI/collaborator assistance. Separate development examples from final evaluation examples. Never invent measurements. Synthetic data must be labeled with its real-world limitations.

## 7. Example learner schedule

With 10–15 hours per week, a first cycle may use week 1 for positioning/jobs, weeks 1–2 for gaps/planning, weeks 2–8 for focused practice, week 2 onward for a truthful resume, week 3 onward for applications/interviews and weekly reviews throughout. A software-oriented eight-week example moves from Python/API basics to a structured LLM workflow, then retrieval/evaluation, then a demonstrable service. Beginners may require substantially longer. Existing skills can skip repeated foundations.

## 8. Resume and portfolio

First present capabilities that are already supported. After practice, add only finished, explainable outcomes. Maintain a master resume, track-specific versions, per-job edits, optional English versions, portfolio and interview notes. Keep facts consistent across versions.

Use problem → action → result → evidence. A stronger statement than a tool list explains the implemented behavior, fixed test set and observed limitations. Add numbers only after measurement. Label plans, simulations and in-progress projects accurately.

## 9. Apply and confirm

Select a role, choose a resume version, prepare factual answers, review requirements, visit the original application channel and record the result. Identity/work eligibility/salary answers must come from confirmed user information. Missing answers remain pending. No automatic submission or fabricated answer is implied by this playbook.

Track saved, preparing, awaiting confirmation, applied, interview/test, offer, rejected, withdrawn and closed as needed. Record source, resume, date, next action and actual confirmation evidence. No response is a waiting state, not a rejection. The scaffold simplifies this into five manual columns.

## 10. Prepare and improve

Prepare short and longer introductions plus project discussions covering problem, alternatives, contribution, results, failures and tradeoffs. Non-engineering roles include adoption, collaboration and business impact. Record interview questions and evidence gaps afterward.

Review effective applications, real replies, interview invitations, stage progression and completed evidence by role, resume version and time cohort. Allow reasonable reply time and avoid conclusions from tiny samples. Low response may involve role level or evidence; technical-test failures may require focused practice; many courses with few artifacts indicate excessive learning scope.

## 11. Success criteria

The first useful outcome is a personal evidence inventory, a bounded current job list, an explainable gap table and executable two-week actions. The platform supports this repeatable cycle without promising a job offer, a fixed transition timeline or a universal interview rate.
